## Главные вопросы (отличия от ядер Doom / Heretic / Hexen)

1. **Плавающая точка.** Quake считает в float почти везде: трансформации и отсечение (`r_bsp.c`, `r_edge.c`,
   `r_draw.c`), перспектива спанов раз в 16 пикселей (`d_scan.c`), модели (`r_alias.c`, `d_polyse.c`), физика,
   QuakeC (`pr_exec.c`: все числа float). У VexRiscv и у ISS (`src/sim/iss.cpp`) расширения F нет. Варианты:
   - **А. soft-float** rv32im (libgcc `__addsf3`, `__mulsf3`, …): работает сразу, медленно — для замера Ф0;
   - **Б. FPU VexRiscv** (`FpuPlugin`, RV32F; генератор SpinalHDL уже стоит с Hexen Ф0б): главный риск — площадь
     (оценить XST), место освобождают OPL3, MIDI и `doom_draw` (Quake они не нужны);
   - **В. fixed-point** в горячих местах (как делали порты на ARM без FPU): много ручной работы, QuakeC — всё
     равно float.
   Решение — по замеру Ф0: число float-операций на кадр, их доля во времени, оценка fps для А и Б.
2. **Память и pak — решение (пользователь, 2026-11-22): pak не грузится целиком, а читается с SD секторами.**
   Куча 8 MB (минимум `MINIMUM_MEMORY` 0x550000 = 5.3 MB), код ~0.5–0.7 MB — в SDRAM, как у Hexen.
   - Quake не держит pak в памяти: открывает его и читает по смещению (`Sys_FileOpenRead` / `Sys_FileSeek` /
     `Sys_FileRead`, `common.c`); карта, модели, звуки, текстуры грузятся в кучу при входе на уровень, во время
     игры pak почти не читается. Нужен только доступ к сектору по номеру.
   - Путь уже есть: OSD-пункт `F` (смонтированный образ; прошивка MCU монтирует любой файл, размер 64 бита),
     ядро просит сектор по LBA (`IMG EVENT` kind 1), MCU отвечает `IMG RDATA` (512 байт) — так работают диски
     uzebox / msx / uknc / quadspeccy (`karabas-go-firmware` origin/master, `docs/link_v2.md`). В SoC тот же
     путь у `doom_sd.v` (файл сохранений).
   - Раскладка: pak0 и pak1 — два пункта `F` (слоты 1 и 2) вместо FL «PAK»; `Sys_File*` переводят смещение в
     сектор и читают через MCU (у PocketQuake это одна функция — `dataslot_read` в `sys_pocket.c`); свободная SDRAM (~15–20 MB после кода и кучи) — кэш секторов (повторный вход
     на уровень, `gfx.wad`, звуки). Один путь для shareware (только pak0), полной версии и модов; загрузка
     FL целиком для Quake не нужна.
   - Цена: загрузка уровня (~2–6 MB чтения) — несколько секунд; скорость SD → MCU → FPGA не замерена (ожидание
     1–3 MB/s), замер на плате в Ф1.
   - Отклонено: сжатие pak в SDRAM (53 MB даже при 2:1 не оставляют места куче), деление pak по эпизодам
     (неудобно, ломает моды).
   - В Ф0 (ISS) pak остаётся в памяти как RAM-файл — на замер это не влияет.
3. **Скорость.** Quake рассчитан на Pentium с FPU; у нас CPI ~2.4 и без FPU. Ещё z-буфер и surface cache —
   много обращений к памяти помимо кадра. Порог для начала — 10 fps, цель 15+. PocketQuake: 100 MHz, D$ 128 KB,
   ускорители спанов / z / моделей — «30+ fps»; у нас 79.5 MHz, D$ 32 KB.
4. **Звук.** Quake сам микширует каналы (`snd_dma.c`, `snd_mix.c`) в кольцо DMA 11025 Hz; нужен PCM-поток в
   `doom_audio` (кольцо в SRAM / BRAM) или микшер в RTL (PocketQuake: `snd_pocket.c` → FIFO 2048, 48 kHz).
   CD-музыка — позже (у PocketQuake `cd_pocket.c`: дорожки .bin с SD), OPL3 / MIDI не нужны.
5. **Ввод.** Клавиатура (коды `quakekeys.h`), мышь (обзор, `+mlook`), геймпад; консоль Quake (`~`).
6. **Сохранения и конфиг.** `config.cfg`, `s<N>.sav` (текст, десятки–сотни KB): файловая система
   `kg_save_fs.c` Hexen подходит.

### Результаты Ф0 (2026-11-22, ветка `f0-iss`)

**Стенд.** `make -C src/fw quake [FLOAT=soft|f] [QARGS=..]` → `build-quake-<FLOAT>/quake.bin` (soft 504 KB, f 449 KB).

### Ф1б — pak секторами через пункты `F` (ветка `f1b-pak`, 2026-11-23)

Решение пользователя: pak не грузится в SDRAM целиком (FL, 15–20 с), а читается с SD по секторам; MCU не трогаем.

- OSD: FL «PAK» (слот 0) заменён на два пункта `F`: **PAK0** (слот 2, Menu+F1) и **PAK1** (слот 3, Menu+F2), `.pak`,
  `/quake`. Прошивка MCU монтирует файл пункта `F` при загрузке ядра заново (`core_loader.cpp`: последний файл
  пункта) и сообщает его размер — после выключения pak выбирать не нужно.
- `doom_sd.v`: `CMD` биты 6..4 = слот образа (0 = файл сохранений, как было), `STAT` биты 3 / 4 = слоты 2 / 3
  смонтированы, `SIZE2` 0x94 / `SIZE3` 0x98 (сохраняются при сбросе ядра: MCU сообщает о монтировании один раз);
  запись разрешена только в слот сохранений.
- Прошивка: `src/fw/quake/kg_pak.c` — `kg_pak_size` / `kg_pak_read`, кэш секторов в свободной SDRAM (бывшая
  область pak 0x10c00000: 32 768 строк по сектору = 16 MB, прямое отображение, теги 128 KB над ними, чистятся при

### Ф7 — растеризатор полигонов вместо сортировки рёбер (ветка `f7-poly` от `f6-cache`, 2026-11-23)

Решение пользователя (цель 25–30 fps в тяжёлых сценах, на плате 11): путь «А + Б» — рендер полигонами с
растеризатором в ПЛИС (А) и свои команды / фиксированная точка на CPU (Б); сначала модель и замер (Ф7а), RTL — после.

#### Ф7а — модель (`POLY=1`, `KG_POLY`)

- В Quake уже есть режим «драйвер берёт полигоны» (`r_drawpolys`: `R_RenderPoly` → `D_DrawPoly`, в программном
  рендере пустой). С `KG_POLY` он включён: BSP обходится как обычно (спереди назад), каждая грань — `R_RenderPoly`
  (копия `r_draw.c`: отсечение по пирамиде видимости, проекция в 12.4), `D_DrawPoly` (копия `d_edge.c`: mip, кэш
  поверхностей, градиенты как у `D_DrawSpans8` Ф3е) отдаёт её блоку: вершины `PVTX`, `PDRAW`. Рёбра, их сортировка
  и спаны (`R_ClipEdge`, `R_ScanEdges`, `R_GenerateSpans`, `D_DrawSurfaces`) не работают вовсе.
- Блок (модель `qspan_model.h` `poly()`): строки ceil(vmin)..ceil(vmax)−1, в строке пиксели ceil(xl)..ceil(xr)−1 (x
  рёбер — DDA в 2^−16 пикселя; соседние грани без щелей и наложений), пиксель — как у перспективы Ф3е. Мир рисуется
  только в ещё не закрытые пиксели: **маска покрытия** (бит на пиксель, 64000 бит = 4 RAMB16; `ZCLR` в начале кадра,
  `ZSPAN` тоже её отмечает) — без сравнения z: 16-битный z Quake вдали груб (~70 единиц на шаг на 1500), а порядок и
  так даёт BSP. Двери / платформы (bmodels, после мира) — сравнение z ≥. Точка пересечения ребра с плоскостью
  отсечения считается от лексикографически меньшего конца — у двух граней ребра она одна.
- Небо и вода (`SURF_DRAWSKY` / `SURF_DRAWTURB`): те же строки в программе, видимые части — по маске (`MADDR` /
  `MDATA`), затем `D_DrawSkyScans8` / `Turbulent8` и их z через `ZSPAN`.
- CPU: проекция вершин мира один раз за кадр (`kg_vproj`: вершина общая у ~3–4 граней, проекция — цепочка FPU с
  делением); грань целиком внутри пирамиды — без отсечения.
- Тайминг `tb_soc`: у `PDRAW` список операций (обращение к SRAM 4 такта / счёт): грань 8 + 4 на вершину + 36 на
  ребро (деление), строка 2, первый отрезок спана 30 (следующие — параллельно пикселям), пиксель мира — маска 1 такт,
  нарисованный — тексель (повтор полуслова не читается) + пиксель (парами) + z; `--qpolys N` — граней в очереди
  (вершины и параметры буферизованы), `--qframe-async`. Стенд: `src/sim/run_poly.sh <имя> [переменные make]`
  (сборка, дамп ISS кадра 30 зала `start`, профиль ISS и `tb_soc` по 12 кадров).
- Картинка (ISS, кадр 32 зала `start`): отличаются ~1 430 пикселей из 64 000 — по краям граней (правило покрытия
  другое, чем у рёбер Quake), на глаз не видно. Разница телепорта и неба между сборками — фаза времени игры
  (`Host_FilterTime` идёт по реальному времени: у сборок разной скорости разные моменты), не ошибка.
- Зал `start`, `tb_soc` (VexRiscv_FPU Ф6), 12 кадров, тактов на кадр / fps при 79.545 MHz:

#### Ф7б — RTL (`quake_span` v3)

- Все записи 0x100..0x1fc — в **очередь команд** (BRAM 512 × 38, первое слово сразу на выходе: команда за такт);

## Ф1б — скорость: кэши 32K / 32K и 79.5 MHz (ветка `f1b-speed`, 2026-11-21)

Плата Mini G (пользователь, счётчик FPS, 16K / 16K, 75 MHz): **16–27 fps по сценам** — как модель.
Решение пользователя: поднять ещё (кэши 32K и частота), программное ускорение — не сейчас.

- `VexRiscv.v`: `GenCoreDefault --iCacheSize 32768 --dCacheSize 32768` (ISS по умолчанию 32K). Verilator, тот же
  отрезок demo1 (кадры 601..620, 75 MHz): 4K 16.1 → 16K 21.4 → **32K 24.3 fps** (+13.5 % к 16K); `tb_rtl`: хэши
  кадров = ISS, ошибок SDRAM 0.
- Частота: из VCO 750 ровно 80 MHz вместе с 25 / 125 не получить; **VCO 875 MHz (50 / 2 × 35)**: clk_sys и clk_sdr
  ÷11 = **79.545 MHz** (+6 %), clk_pix ÷35 = 25, HDMI ÷7 = 125, FT ÷105 = 8.33 — пиксельные и HDMI-частоты точные.
  Пока только Mini G; Go / Mini — 75 MHz (их сборка — при выпуске).
- Что зависело от частоты: `doom_soc` — `CLK_NUM / CLK_DEN` (MHz) вместо `MS_DIV` и делителя 75: US — дробный
  счётчик (+CLK_DEN за такт, тик при ≥ CLK_NUM), MS — из US (1000 мкс), точно при 875 / 11; `doom_audio` —
  `CLK_HZ` (MIDI 31250) и `OPL_STEP` (49716 Hz: 2847048 при 75 MHz, 2684359 при 79.545). SDRAM: регенерация
  560 тактов = 7.04 мкс (< 7.8), INIT 16000 = 201 мкс (≥ 200); окна SDRAM / SRAM по абсолютному времени
  сходятся (SRAM: 2 такта = 25.1 нс). По умолчанию (75 MHz) `tb_rtl` бит в бит как раньше.

## Ф1 — проект (ветка `f1-minig`, 2026-11-18)

Проверки перед RTL:
- Кадры ISS выгружены в картинки (`iss --shot F file.ppm`): DOOM2 MAP01 рисуется верно (вид, оружие, статус-бар,
  сообщения). В строке кадра ISS теперь хэш FNV-1a кадра + палитры — эталон для RTL.
- Невыровненных обращений нет: ISS считает их (0 за 1300 кадров demo1), все lump-ы DOOM2.WAD и DOOM.WAD (1.9)
  выровнены на 4. Готовый VexRiscv ловит невыровненные (`catchUnaligned`) — в прошивке нужен обработчик ловушки
  (сообщение на экран; эмуляция загрузки — если встретится PWAD с невыровненными lump-ами).
- Doom рисует статус-бар разностно (`ST_diffDraw`), рамку — `borderdrawcount` раз: **кадр должен жить в одном
  постоянном буфере**. Поэтому: CPU рисует в рабочий буфер SRAM 0x3f0000; по записи «кадр готов» аппаратный DMA
  копирует его (64000 байт) в один из двух буферов показа, смена буфера показа — в гашении (без разрывов).
  Шаг 1 — показ прямо из рабочего буфера (с разрывами), DMA — шаг 2.
- Перезапуск при новом WAD: CPU в сбросе, программа стартует заново; `.data` копируется crt0 из нетронутого образа
  (LMA в области программы), `.bss` обнуляется — перезагружать программу не нужно.
- ROM в .kg: блок с длиной в 4 байта — программа ~420 KB идёт в `roms` (адрес 0 = SDRAM 0x10000000).

Решения (Claude, не подтверждены):
- **Такты** (один PLL, VCO 750 = 50 × 15): clk_sys 75 MHz (CPU, шина, SDRAM, SRAM, kg_mcu2), SDR_CLK 75 MHz 225°
  через ODDR2 (схема archie, проверена на Mini G при 80), clk_pix 25 MHz, HDMI 125 MHz и 125 MHz 180°, FT_CLK_OUT 8.33.
  Если PAR не даст 75 — 62.5 MHz (VCO 750 / 12).
- **Видео**: 640x480@60 (25 MHz вместо 25.175 — мониторы берут), 320x200 удвоено в 640x400 по центру, чёрные поля
  40 строк сверху и снизу; синхро и de всегда; OSD link v2 поверх; HDMI со звуком (Ф2).
- **Карта памяти CPU**: 0x00000000 SRAM 4 MB (рабочий кадр 0x3f0000, буферы показа 0x3e0000 / 0x3d0000),
  0x10000000 SDRAM 32 MB (программа + zone + стек: 12 MB; WAD 0x10c00000, до 20 MB), 0x80000000 MMIO
  (как `src/fw/mmio.h` + клавиши, мышь, джойстик).
- **SDRAM** (`doom_sdram.v`, по образцу archie_sdram): один порт — CPU (строка кэша = 8 слов одной серией READ
  в открытой строке, слова по мере прихода; запись слова с маской) или загрузчик, пока CPU в сбросе. CL2, BL1.
- **SRAM** (`doom_sram.v`): порт CPU (байт / полуслово / слово), порт видео (строка 320 байт в буфер строки,
  приоритет), позже DMA.
- **Загрузка**: ROM (kind 0) → программа; FL слот 0 «WAD» (.wad, каталог /doom) → 0x10c00000, MMIO_WADSIZE по
  концу загрузки; CPU в сбросе, пока идёт любая загрузка. Программа ждёт WAD.
- **Ввод**: PS/2-коды kg_mcu2 в FIFO (MMIO) → коды Doom в прошивке; мышь (сумма dx / dy, кнопки), джойстик.
- **Проверка до платы**: Verilator всего SoC (без mcu / HDMI) с моделями SDRAM (по командам) и SRAM, старт из
  дампа ISS, хэши кадров = ISS; там же замер тактов на строку кэша → `model.py`. Затем первый PAR скелета (Mini G).

### Ф1.3 — первый запуск на плате и копия кадра DMA (2026-11-18)

- 26111801 на Mini G: экран ожидания WAD, затем **DOOM II с DOOM2.WAD (FL с SD1) играет**: демо, меню (Esc),
  клавиатура работает. FL 15 MB грузится ~25 с (~0.6 MB/s).
- Прошивка: при `debug=1` сторож зависаний сбрасывал плату через ~8 с загрузки FL (11 и 15 MB). Исправлено в
  прошивке (PR #155, релиз v26111811): шаг сторожа на каждый блок `core_send_file` + `[setup] watchdog`.
  С 26111811 и `debug=1` WAD грузится без сброса.
- Мигание спрайтов (пользователь): показ шёл прямо из рабочего буфера, а спрайты Doom рисует последними.
  Исправлено: по записи FRAME `doom_sram` копирует DMA кадр (64000 байт, ~2.6 ms) в скрытый буфер показа
  (0x3e0000 / 0x3d0000), CPU ждёт SRAM на время копии; видео берёт новый буфер в начале кадровой синхронизации.
  tb_rtl: копии = кадрам бит в бит. DEBUG_DATA = { fps за последнюю секунду, кадры }.
- PAR: 4929 LUT (32 %), 49 % слайсов, все ограничения выполнены. **На плате: 20–25 fps в игровом демо DOOM II**
  (заставки 60), как прогноз Verilator (~24).
